# EDA

## Подготовка датасета

### Проблема

На текущем этапе работы над проектом нет настоящего микросервисного проекта, с которого могли быть сняты данные, поэтому в рамках работы над проектом было решено обойтись синтетическим набором данных.

### Генерация датасета

Для генерации датасета был использован ChatGPT (GPT-6 Уровень усилий рассуждения "Высокий"), в который был отправлен следующий промт:

```
Я разрабатываю учебный ML-проект Semantic Firewall. Его задача: обнаруживать семантические breaking changes между микросервисами, когда структура API не меняется, но новое поведение одного сервиса нарушает ожидания других.
Необходимо создать полностью синтетический, воспроизводимый датасет для проведения EDA и последующего обучения бинарного классификатора.

1. Требования к данным

Создай небольшую модель e-commerce системы на Python с сервисами-поставщиками и зависимыми сервисами-потребителями.
Примеры изменений поведения:

- Цена начинает включать налог вместо цены без налога.
- Изменяется порядок расчёта скидок и комиссий.
- Меняются единицы измерения.
- Изменяется округление денежных значений.
- Меняется порядок сортировки результатов.
- Изменяются граничные условия или значения по умолчанию.
- Меняется поведение повторных запросов или обработка статусов.

Во всех сценариях структура API должна оставаться неизменной: названия публичных методов, аргументы и структура возвращаемых данных должны сохраняться. Изменяться должна именно семантика работы.
Для каждого изменения создай несколько зависимых потребителей. Одно изменение должно иметь возможность оказаться breaking для одного потребителя и non-breaking для другого.
Не делай все примеры однотипными. Используй разные сервисы, изменения логики и способы обработки результатов.
Целевой объём: около 400 пар (изменение, потребитель), сгруппированных по семействам сценариев.

2. Формирование разметки

Не назначай метки случайно или только на основании описания сценария.

Для каждого изменения сохрани:

- Исходную версию Python-кода provider.
- Изменённую версию provider.
- Git diff между версиями.
- Неизменённый код consumer.
- Набор проверок ожидаемого поведения consumer.

Получай метку через выполнение одинаковых контрактных проверок на старой и новой версиях provider.

Правила разметки:

- label = 1 (breaking): тесты со старой версией проходят, а с новой возникает воспроизводимое нарушение контракта.
- label = 0 (non-breaking): тесты проходят с обеими версиями.
- Если старая версия не проходит проверки или результат неоднозначен, исключай пример из основного датасета.

Используй несколько тестовых входов для каждого потребителя.

Важно: label = 0 означает совместимость только в пределах проверенных сценариев, а не абсолютную гарантию отсутствия ошибок.

3. Формат датасета

Единица наблюдения: пара (изменение кода provider, consumer).

Создай CSV с полями:

- pair_id, scenario_id, family_id
- provider, consumer
- change_type
- diff_path
- provider_old_path, provider_new_path
- consumer_code_path
- lines_added, lines_deleted, diff_chars
- api_schema_unchanged
- label
- split

Исходный код и Git diff храни в отдельных файлах. В CSV должны находиться метаданные и ссылки на них.
Отдельно сохрани граф зависимостей между сервисами и технический журнал получения меток.

4. Проверки качества

После генерации автоматически проверь:

1. Все пути к исходным файлам существуют.
2. Метки соответствуют результатам повторного выполнения тестов.
3. API-схема остаётся неизменной на проверяемых входах.
4. Датасет содержит оба класса и разные категории изменений.
5. Нет полностью одинаковых Git diff, выдаваемых за независимые изменения.
6. Связанные варианты одного сценария не попадают одновременно в train и test.
7. В признаки будущей модели не попадают метки, результаты тестов и эталонные ответы.
Раздели данные на train, validation и test по family_id, а не случайно по строкам.
Если проверка не проходит, исправь генератор и повтори валидацию. Не скрывай обнаруженные проблемы.

5. Воспроизводимость

Предоставь Python-скрипт для генерации датасета, чтобы все примеры и метки можно было воспроизвести.
Результат должен включать CSV, исходники сервисов, Git diff, контрактные тесты, граф зависимостей.
Учитывай, что это учебная симуляция: взаимодействие сервисов можно реализовать прямыми вызовами Python-модулей без HTTP и сетевой инфраструктуры.
Не утверждай, что полностью синтетические данные отражают реальные production-инциденты. Отдельно опиши риск того, что будущая ML-модель выучит особенности генератора, а не общие закономерности семантической совместимости.
```

### Структура датасета и запуск

Основная таблица находится в `data/processed/pairs.csv`. Каждая строка описывает пару `(изменение кода, потребитель)`: сервисы, тип изменения, пути к исходникам и Git diff, метку `label` и часть выборки `split`.

Остальные файлы:

- `data/processed/scenarios.csv`: описание изменений и их семейств.
- `data/processed/dependency_edges.csv`: связи между сервисами.
- `data/raw/scenarios/`: старая и новая версии provider, код consumers и Git diff.
- `data/audit/`: контрактные тесты, журнал разметки и результаты проверки.
- `notebooks/eda.ipynb`: анализ данных с таблицами и графиками.

Метка `label=1` означает, что старый provider проходит проверки потребителя, а новый нарушает хотя бы одну. При `label=0` обе версии проходят все три проверенных случая. Это не гарантирует совместимость на любых входных данных. Проверки выполняются прямыми вызовами Python-модулей, без HTTP.

Данные разделены на train, validation и test по `family_id`. Все варианты одного семейства находятся в одной выборке. Идентификаторы пар и сценариев, `family_id`, `split`, `label` и содержимое `data/audit/` не используются как входные признаки модели.

Датасет можно заново создать командой `python scripts/generate_dataset.py`. Генератор перезаписывает исходники в `data/raw/scenarios/` и тесты в `data/audit/contracts/`. Исходники сценариев не следует автоматически форматировать: сохранённые Git diff должны соответствовать этим файлам.

## Анализ датасета

### Объём и структура

Для анализа использовались pairs.csv, scenarios.csv, dependency_edges.csv и результаты проверки контрактов из validation_results.json.

Посчитано количество наблюдений, уникальных изменений, семейств сценариев, типов изменений и связей между сервисами.

- 405 пар (изменение кода, потребитель).
- 81 уникальный Git diff, 27 семейств мутаций, 11 типов изменений.
- 9 сервисов-поставщиков, 23 сервиса-потребителя, 54 ориентированные зависимости.
- Для каждого Git diff предусмотрены пять потребителей, для каждого потребителя три контрактных случая.
- Один Git diff встречается в пяти строках датасета, так как его влияние проверяется на разных потребителях. Поэтому 405 пар нельзя считать 405 независимыми изменениями.

### Разнообразие изменений

Для каждого change_type посчитаны количество пар, количество breaking-примеров и их доля.

| Тип изменения | Пар | Breaking | Breaking rate |
| --- | ---: | ---: | ---: |
| boundary_condition | 75 | 55 | 73.3% |
| fallback_policy | 60 | 48 | 80.0% |
| idempotency | 45 | 30 | 66.7% |
| unit_conversion | 45 | 33 | 73.3% |
| value_semantics | 45 | 27 | 60.0% |
| enum_semantics | 30 | 27 | 90.0% |
| calculation_order | 30 | 14 | 46.7% |
| ordering | 30 | 24 | 80.0% |
| normalization | 15 | 9 | 60.0% |
| temporal_semantics | 15 | 9 | 60.0% |
| rounding | 15 | 5 | 33.3% |

В данных встречаются изменения налоговой логики, расчёта комиссий, округления, единиц измерения, порогов, сортировки, статусов, идемпотентности и обработки значений по умолчанию.

Каждый тип содержит оба класса, но доли breaking существенно отличаются. Например, для enum_semantics это 90%, а для rounding только 33.3%.

Модель может использовать тип изменения как подсказку вместо анализа поведения сервисов. Это нужно учитывать при интерпретации результатов.

Доли нарушений зависят от сгенерированных сценариев и выбранных тестов. Они не отражают частоту подобных инцидентов в реальной разработке.

### Размер изменений и влияние на потребителей

Для каждого уникального scenario_id были рассчитаны:

- Размер Git diff в символах.
- Количество потребителей с label=1.
- Доля затронутых потребителей среди пяти проверенных.

Длина Git diff находится в диапазоне от 232 до 541 символа, медиана составляет 342 символа. При этом одно изменение может нарушать контракт от одного до пяти потребителей.

Это показывает, почему недостаточно анализировать только Git diff. Влияние одного изменения зависит от того, как конкретный consumer использует результат provider.

Например, в сценарии price_tax_inclusion_v01 сервис расчёта цены начинает включать налог в поле total. При этом CustomerPortalService использует total для расчёта категории суммы. Значение категории может измениться, хотя структура ответа provider осталась прежней.

Поэтому в основной модели нужен код потребителя, а не только размер и текст изменения.

### Зависимости между сервисами

По полям provider и consumer построена таблица частот взаимодействий. Она позволяет проверить, какие связи представлены в датасете и сколько наблюдений приходится на каждую пару сервисов.

Всего представлено 54 ориентированные зависимости.

Граф зависимостей задан вручную. Он подходит для проверки MVP, но не отражает реальную топологию микросервисной системы.

## Разбиение

Для проверки разбиения посчитано количество наблюдений каждого класса в train, validation и test.

| Часть | Пар | Non-breaking | Breaking |
| --- | ---: | ---: | ---: |
| train | 285 | 85 | 200 |
| validation | 60 | 16 | 44 |
| test | 60 | 23 | 37 |

Дополнительно проверено, что каждый family_id и scenario_id встречается только в одной части датасета.

Это необходимо, поскольку несколько вариантов одного изменения могут отличаться реализацией, но сохранять одинаковую логику. При случайном разделении строк похожие изменения могли бы оказаться одновременно в train и test.

Разбиение по family_id снижает риск такой утечки.

При этом в test всего четыре независимых семейства. Несмотря на 60 наблюдений, по ним пока нельзя надёжно судить о способности модели работать с принципиально новыми видами изменений.

## Выводы

1. Для baseline использовать Git diff из diff_path и ID сервиса из consumer. Эти данные доступны при анализе PR и соответствуют постановке задачи из дизайн-документа.

2. Для основной модели дополнительно использовать provider_old_path, provider_new_path, consumer_code_path и граф зависимостей. Проверка влияния одного diff на разных потребителей показывает необходимость такого контекста.

3. Не использовать split, family_id, результаты контрактных тестов и эталонные ответы как признаки. Эти данные предназначены для разбиения и разметки, их использование приведёт к утечке информации.

4. Оценивать Recall, Precision, PR-AUC и FPR. Из-за дисбаланса классов accuracy может давать завышенное представление о качестве.

5. Сохранять разбиение по семействам изменений. Оценка на случайно перемешанных строках будет недостаточно надёжной из-за повторяющихся Git diff и родственных сценариев.

6. Для более убедительной оценки необходимо увеличить количество независимых семейств изменений. Текущего набора достаточно для EDA и первого эксперимента с моделями, но не для выводов о качестве на реальных проектах.

### Ограничения

- Это полностью синтетический датасет. Сценарии составлены вручную, а код и тесты сгенерированы из конечного набора спецификаций.

- Метки построены по golden-master тестам, зафиксированным со старой версии. Они позволяют воспроизвести регрессию, но не доказывают, что каждый тест соответствует реальному бизнес-контракту.

- label=0 означает отсутствие нарушения в трёх проверенных случаях, а не совместимость для всех возможных входных данных.

- Взаимодействие сервисов реализовано через вызовы Python-модулей, без сети, брокеров и HTTP API.

- Примеры ограничены e-commerce и Python. Код и изменения проще реальных микросервисов.

- Роли потребителей и количество зависимостей заданы вручную. Для каждого изменения используется одинаковое количество потребителей.

Количество независимых семейств невелико. Даже при отсутствии пересечений между train и test модель может запомнить особенности генератора.

Датасет подходит для учебного EDA и сравнительного эксперимента, но не доказывает, что будущая модель будет хорошо работать на реальных PR. Для такой проверки понадобятся реальные изменения кода и независимая экспертная разметка.
